- 2026-06-05：前端工作台流程和易用性走查问题（已处理）。
  - 来源：在本地 InMemory 示例数据中走查完整链路：新建项目 -> 新增资料 -> 读取资料 -> 证据核验 -> 抽取 Claim -> 合成 Requirement -> 人工审核 -> 生成任务 -> 导出 Markdown。
  - 处理状态：当前代码已将 Claim 抽取前置条件收紧为“存在证据块、无 Pending 证据块、至少一个 Confirmed 证据块”，失败时展示后端错误；Requirement 详情展示来源 Claim、证据、版本记录和审核记录；批准后跳转任务阶段并预选已批准需求；任务阶段增加 Approved Requirement 选择器；任务详情展示来源 Requirement / Version、Evidence、Missing Context 和 Assumptions；任务就绪度按 0..100 渲染；主要 mutation 使用成功/失败反馈。
  - 剩余关注：后续继续修改 UI 时仍需复查 Ant Design v6 废弃 props、键盘可达性、窄屏 Drawer 操作区和多 Approved Requirement 时的重复生成确认。
  - 验证：相关变更后至少运行 `cd frontend && npm.cmd run build`；涉及后端 DTO/API 时同时运行 `dotnet test ProjectContextCompiler.slnx`。手工冒烟按 `docs/testing.md` 覆盖“项目列表 -> 新建项目 -> 六阶段切换 -> 证据块表格与详情 Drawer -> 批量确认/忽略 -> Claim Gate -> 审核 Modal -> 批准后任务来源预选 -> 诊断页签 -> 窄屏布局”。

- 2026-06-05：前端工作台视觉和响应式设计走查问题（已处理）。
  - 来源：按企业后台和 `uncodixfy` 标准检查当前 Ant Design 工作台；真实后端因 NuGet TLS/凭证问题无法启动时，使用只返回前端契约数据的临时 mock API 检查有数据状态，并用 390px 宽度检查窄屏布局。
  - 处理状态：已在 `frontend/src/App.tsx` 和 `frontend/src/styles.css` 收敛阶段导航、条件提示、窄屏详情入口、Drawer 操作区、响应式表格列和详情区卡片层级。后续若继续改 UI，仍应按本条验证清单复查。
  - 结论：当前页面整体方向正确，已经避免了典型 AI 风格的英雄区、强渐变、玻璃拟态、夸张圆角和装饰性阴影；主要问题集中在窄屏详情可达性、信息密度和说明型文案噪声。
  - 影响：这些问题不会破坏核心流程，但会降低人工审核工作台的日常效率。尤其在证据核验和需求审核阶段，用户需要快速扫描列表、打开详情、确认依据并做决策；若详情入口不显式、表格横滚过重或提示文案长期占据注意力，会让后台界面更像模板化演示页而不是高频业务工具。
  - 问题 1：窄屏详情入口发现性不足。`stage-detail` 在 `max-width: 980px` 下隐藏，详情只能通过点击表格行打开 Drawer；但表格行没有显式“查看详情”操作，用户不一定知道可点击。
  - 建议 1：窄屏下给每行保留明确的“查看详情”操作，或把标题/主列做成可点击链接；Drawer 标题显示当前对象名称，列表区域保留选中态。证据核验、Claim、需求审核、任务和导出阶段都应复用同一模式。
  - 问题 2：窄屏表格过度依赖内部横向滚动。项目列表、资料、证据核验、需求审核等表格通过 `scroll.x` 承载 620px 到 860px 的宽表；390px 宽度下全页不溢出，但关键列和操作列需要横向滑动才能看到。
  - 建议 2：窄屏表格保留 2 到 3 个高价值列，把状态、置信度和操作收敛到主列摘要、行内更多菜单或 Drawer 操作区；审核类动作优先放在详情 Drawer 底部的固定操作区，而不是只放在横滚表格右侧。
  - 问题 3：阶段导航说明文字偏多。六阶段导航同时展示阶段名称和一句功能说明，桌面端可读但信息重复；窄屏虽然切到 Select，DOM 和可访问文本仍包含长说明。
  - 建议 3：阶段导航默认只保留编号、图标、名称和状态；功能说明只在空状态、阻塞状态或帮助入口中出现。这样能减少模板化说明文，保持后台工作台的扫描效率。
  - 问题 4：常驻“下一步” info Alert 容易变成噪声。每个阶段都显示提示，即使流程没有阻塞也持续占据主内容顶部。
  - 建议 4：将常驻下一步提示降级为条件提示：只在空状态、Gate 阻塞、错误或可恢复动作缺失时显示；正常有数据状态下用按钮禁用原因、空态文案或局部提示表达下一步。
  - 问题 5：详情区卡片层级偏重。`stage-detail` 本身是 Card，需求详情内部又使用多个 Card 和 section，复杂需求时容易形成“卡片套卡片”的视觉层级。
  - 建议 5：详情区保留一个外层容器即可；内部内容优先使用 `Descriptions`、分组标题、分割线和轻量列表。只有版本记录、审核材料、Agent Prompt 等需要独立边界的内容才使用 Card 或 Tabs。
  - 验证：修复后运行 `cd frontend && npm.cmd run build`；再用桌面宽度和 390px 窄屏手工检查项目列表、证据核验、需求审核和任务阶段，确认无全页横向溢出、详情入口可见、关键动作无需依赖横滚、常驻说明文案减少且 Gate 阻塞仍有明确提示。
